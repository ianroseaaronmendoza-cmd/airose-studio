🌐 Airose Studio — Clean Architecture Overview
1. Purpose

Airose Studio is a static React website with a local-only editing system.
The site deployed to Vercel contains no dynamic backend, but when the developer runs pnpm dev, a custom Webpack Dev Server enables:

Creating content

Editing content

Reordering content

Saving content to disk

Content is saved as JSON files under /data, which is the single source of truth for the entire website.

Publishing to production is done manually using a GitHub commit script.

4. Environment Philosophy
✔ Local dev = Editor Mode ON
✔ Production = Static, No Editing
✔ All editable content stored as JSON

No database, no backend, no API server.

5. Core Architectural Rules
Rule 1 — DATA = JSON files

Everything in the site is driven by:

/data/<category>/<slug>.json


These files are manually editable or generated by the in-site editor.

Rule 2 — Editing is LOCAL-ONLY

The editing toolbar, UI controls, save buttons, and editors appear only when pnpm dev is running.

On Vercel:

No saving

No dev server

No editors

Only static rendering

Rule 3 — Saving happens through Webpack Dev Server

webpack.config.js registers multiple routes, for example:

POST /dev/sections/save
POST /dev/blog/save
POST /dev/poem/save
POST /dev/project/save


These routes call Node scripts in dev-tools/ to write JSON to disk.

Rule 4 — Unified Persistence Layer (frontend)

All frontend saving uses:

src/lib/persistence/


Including:

http.ts

result.ts

sections.ts

This removes duplication and enforces a consistent flow:

UI → Hook → Persistence → Dev Server → JSON File

Rule 5 — Static Rendering

All pages read data directly from:

/data/** (imported at build time)


When deployed, pages use static JSON downloaded from the public/data folder.

Rule 6 — Publishing to Production

The workflow is:

You edit locally

Edits create/overwrite JSON in /data/**

You run:

pnpm publish:content


Script walks the /data folder

Builds a Git commit using Octokit

Pushes to GitHub

Vercel receives a deploy hook

New static site goes live

6. Sections System (New Modular Architecture)

A major architectural feature:

🧱 Section Blocks

Pages can be made of flexible “blocks”:

Text

Image

Title

Heading

Quote

Scripture

Custom content

Rich Text (Tiptap content)

🧬 Structure saved as:
{
  "slug": "my-page",
  "title": "My Page",
  "sections": [
    {
      "id": "sec_123",
      "type": "text",
      "content": "Hello world"
    },
    {
      "id": "sec_456",
      "type": "image",
      "url": "/uploads/123.png"
    }
  ],
  "updated": 123456789
}

🛠 Editors use:

src/lib/hooks/useSectionsEditor.ts

📁 Saved into:

data/sections/<slug>.json

9. Technical Summary (for AI assistants)
✔ React SPA, client-side routing
✔ Webpack dev-server for local data writes
✔ No backend in production
✔ JSON is the database
✔ Editor Mode only exists locally
✔ Dev-tools = local “file system API”
✔ GitHub commit script handles deployment
✔ Unified persistence layer handles all saving
✔ All page content lives under /data/**
10. Best Practices for Copilot / AI Tools

Use native fetch, no Axios

Use the Result<T> pattern

Use unified persistence (never call dev-tools directly)

Always write to /data/**

Respect Editor Mode boundaries

Avoid server-dependent logic

Preserve static compatibility
